# 02 — 稿件单一数据源

## 一句话主张

没有结构化内容模型，局部编辑、换主题、质量检查和原生导出都会同时垮掉。

## 问题场景

产品经理要改第 3 页第二个要点；设计师要换皮肤；你还要检查是否超框——若真相是一坨 HTML，这三件事会互相踩脚。

## 错误做法

- 以渲染结果（DOM/图片）为存储真相；  
- 预览一份数据、导出再让模型「重新写一版」；  
- 把坐标、文案、颜色揉进同一个无法拆分的大字符串。

## 设计抉择

- **稿件（Deck）**聚合大纲、页面、主题与修订；  
- **页面**由**内容块** + **布局**描述构成；  
- **主题（Theme）**只作用视觉；  
- 一切写操作都落在内容模型上。  

几何可用归一化或求解结果缓存，但「可编辑语义」必须留在块级结构里。

## 羽师中的对应模块

- P0-05 内容模型  
- P0-11 布局与主题分离  
- 术语：稿件、页面、内容块、布局、主题（Theme）

## 演示脚本

1. 展示一份「同一页」的三种视图：JSON/模型摘要、Web 预览、导出后可改文本；  
2. 只改模型里的一句话，预览与导出语义一起变；  
3. 只换 Theme，文案位置语义不变（允许皮肤变）；  
4. 总结：模型是总线，渲染器是插件。

**口播时长建议：** 10–15 分钟。

## 练习 / 作业

为「标题 + 三个要点 + 一张图」设计最小内容块列表（只写字段名与含义，不写代码）。

## 下期钩子
