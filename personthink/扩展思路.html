多模型适配和成本优化

目前项目默认对接 DeepS⁢⁢⁢eek 的 OpenAI 兼容接口，通过环境变量切换 ؜؜؜Base URL 和模型名。但实际使用中，不同模型的质⁢⁢⁢量和成本差异很大，同一个提示词在 GPT-4o 和 D‎‎‎eepSeek 上的表现也不一样           ​​​                     

一个实用的优化方向是做模型路由。根据任务类型选择不同的模型：大纲生成需要全局视野，可以用更强的模型；单页内容生成是批量任务，更关注性价比，可以用轻量模型。路由逻辑可以写在 StructuredChatClient 的上层，根据 task_type 参数分发到不同的模型配置。

成本控制方面，可以在 llm/client.py 里加一个 hook，每次模型调用后记录 input/output token 数，按用户和项目汇总写入数据库。有了这些数据，就能做出按用户的用量统计面板，也能在总成本接近预算时触发告警。如果做成产品，这套计量系统就是按量计费的基础。2bhDrmoeBtrmxXJMuaKJn/W+90arS0u/yfD9HsADPaY=

再进一步，可⁢⁢⁢以做 token 预算机؜؜؜制。在生成前根据页数估算⁢⁢⁢总 token 消耗，超‎‎‎过预算时提前告知用户，而​​​不是跑到一半才发现额度不够。

AI 编辑能力增强

目前的 AI 编辑支持对单页内容做修改，通过 bind_tools 调用编辑工具。但用户的编辑意图往往不局限于单页。uS6ZfTP1Mg7eSJ1DjzEb5vW1Tkl5CAuGldbfDiybVgk=

第一个方向是多轮对话记忆。当前每次 AI 编辑是独立的一轮调用，用户说 “把标题改短一点” 之后再说 “再短一些”，第二次调用不知道第一次做了什么。可以在 EditSession 中维护一个对话历史列表，把前几轮的用户指令和模型操作作为上下文传入。历史条数用滑动窗口控制，避免上下文过长。

第二个方向是跨页编辑。用户说 “所有页面的标题都改成问句格式”，目前需要逐页操作。可以在编辑指令解析层增加一个 “作用范围” 参数（当前页 / 选中的几页 / 全部），然后对每页独立调用编辑工具。跨页编辑本质上是批量的单页操作，复用现有的 EditSession 即可，但需要注意并发冲突和 revision 递增。

第三个方向是风格迁移⁢⁢⁢。用户上传一张喜欢的 PPT 截图，A؜I 提取其配色、؜؜字体、排版风格，生成一⁢套自定义主题。这需要多模态模⁢⁢型的支持，‎先做图片理解提取风格特征，再映射到主题​‎‎ JSON 的调色板和字体栈            ​​                    A5yGssbA+XlqiLrR97jc/ZP/BqZbk4LkBstTxPdiC4w=

更多输入源支持

项目目前支持⁢⁢⁢主题文字、长文本和文档؜؜؜（PDF/DOCX/M⁢⁢⁢arkdown/TXT‎‎‎）三种输入方式。实际场​​​景中，内容来源远不止这些。

URL 输入是最直接的扩展。用户贴一个网页链接，后端抓取页面正文提取文本，走和长文本一样的后续流程。可以用 httpx + readability 或 trafilatura 做正文提取，过滤掉导航栏、广告等噪音内容。需要注意超时控制和内容长度截断。20JHsCYdVd/U/giWcVh07DdsFx8w9W26jXMMEsNFmJk=

语音转文稿也是一个高⁢⁢⁢频场景。会议录音、课程录音转成 PPT，؜؜؜省去手动整理的时间。接入 Whisper⁢⁢⁢ API 或阿里云语音识别服务，把音频转‎‎‎成文本后走正常的生成流程。前端需要增加一​​​个音频上传入口和转写进度展示。

OCR 识别可以处⁢⁢⁢理手写笔记、白板照片等场景。用户拍一؜؜؜张照片上传，后端用 OCR 服务提取⁢⁢⁢文字。和图片理解不同的是，OCR 只‎‎‎提取文字，不做内容理解，所以输出是纯​​​文本，直接进入已有的输入解析管线。

协同编辑和版本管理

当前项目是单⁢⁢用户⁢编辑模式，一个项目؜؜只有创建者能访؜问。如果⁢⁢多人同时编辑同一份 P‎‎PT，⁢现有的 revi​​sion 乐观锁会频‎繁冲突                 ​               

引入协同编辑需要解决两个核心问题⁢⁢。第一是⁢实时同步，可以用 WebSocket 替代当前的 REST 保存，؜؜基于 CRDT 或؜ OT 算法做冲突合并                                不⁢过这个改动量很大，一个折中⁢⁢方案是 “页级锁”：某人正在编辑第 3 页时，其他人看到的‎第 3 页会‎‎标记为 “正在编辑中”，不允许同时修改，但可以编辑其他页面      ​​​                          

第二是版本管理。每次保存时除了递增 revision，还在一张 deck_versions 表里存一份完整快照。用户可以在历史版本列表中预览和回滚。快照可以做增量压缩，只存和上一个版本的 diff，用 JSON Patch 格式。gFVrYVzxL8tKUz/34qdnmJpTKEG8xBm2b32DT6NwTSc=

协同编辑是简历上非常有⁢⁢⁢区分度的亮点。即使只做到 “页级锁 + 版؜؜؜本历史” 这个程度，面试时也能聊实时同步的⁢⁢⁢技术选型、乐观锁的局限性、CRDT 和 O‎‎‎T 的权衡                ​​​                

模板市场和用户自定义主题

项目自带 ⁢4 ⁢⁢套主题，但用户؜的审美需求千差⁢万؜؜别。如果能让用户创建‎和分享自⁢⁢己的主题，​产品价值会大幅提升 ‎‎                ​​               A5yGssbA+XlqiLrR97jc/ZP/BqZbk4LkBstTxPdiC4w=

最小实现是在前端增加一个主题编辑器，让用户调整调色板（主色、辅色、背景色、文字色）、字体栈和装饰形状。编辑器的数据结构完全复用现有的主题 JSON 格式，保存到数据库的 user_themes 表中。切换主题时，先从用户自定义主题里查，查不到再从 shared/themes/ 加载内置主题。

再进一步可以做模板市场⁢⁢⁢。模板 = 主题 + 一组预设的布局搭配。用户做出؜؜؜好看的 PPT 后，可以把当前的主题和各页布局保⁢⁢⁢存为模板，发布到市场供其他人使用。模板市场需要增‎‎‎加浏览、搜索、收藏、使用量统计等功能，工作量不小​​​，但做完之后项目的产品完整度会上一个台阶。

自定义布局模板也很有价值。目前的布局定义在 shared/layouts/ 的 JSON 文件里，通过 slots 描述容器位置和接受的块类型。如果让用户通过拖拽创建自己的布局并保存，就能覆盖更多排版需求。A5yGssbA+XlqiLrR97jc/ZP/BqZbk4LkBstTxPdiC4w=

智能排版升级

目前的灵活排⁢⁢版通⁢过布局树 + sol؜؜ver 实现，用؜户可以拖⁢⁢动分隔线调整比例、在候选排布⁢‎‎中切换。但排版方案的​​选择仍然需要‎用户手动操作              ​                  

一个方向是自动配色建议⁢⁢⁢。根据用户上传的 logo 或指定的؜؜؜品牌色，AI 自动生成一套和谐的调色板⁢⁢⁢，应用到主题中。可以用色彩理论算法（互‎‎‎补色、类比色、三元色）生成候选方案，也​​​可以让多模态模型根据品牌调性推荐。HJbB3btdiEuUkXNxIOa41rNrviFZ79ZqC7wVhWRhi8k=

另一个方向是视觉评分⁢⁢⁢。给生成的每一页打一个排版分数（文字密度、留白比例؜؜؜、对比度、视觉平衡），分数低的页面自动建议优化⁢⁢⁢方案。评分规则可以从设计规范中提炼：标题字号不‎‎‎小于正文的 1.5 倍、正文行数不超过 8 行​​​、图片面积占比 30%-50% 等。

还有一个实用的优化：根据内容自动选择最佳排布。当前 AI 生成页面时只指定了 layout_id，灵活排版的布局树由固定预设给出。可以在生成阶段根据块的数量和类型，从候选预设中选出最匹配的排布。比如 3 个要点 + 1 张图，应该用左右分栏；5 个 KPI，应该用五列等宽。

性能和可观测性

项目在开发⁢⁢⁢阶段够用，但如؜果؜面؜向真实用户⁢，性⁢能和⁢可观测‎性需要‎系统‎性加​强。

最紧迫的是接入监控。在 FastAPI 中集成 Prometheus 客户端，暴露 /metrics 端点，采集请求延迟分布、队列深度、Worker 活跃数、LLM 调用耗时和成功率等指标。配合 Grafana 做可视化面板，一眼就能看到系统健康状况。

异常追踪接入 Se⁢⁢⁢ntry，自动捕获未处理的异常和慢请؜؜؜求。模型调用失败的告警尤其重要，⁢⁢⁢因为如果 DeepSeek 服务不‎‎‎可用，所有生成任务都会失败，需要第​​​一时间发现并切换到备用模型。IO3kPKw7IgUq3xDeAGIgrjh6IagmiW1AQhC3eR6VnPY=

性能优化方面，有几个低成本高收益的点。布局和主题 JSON 目前前端通过 import.meta.glob 在构建期加载，如果主题数量增多，可以改为按需加载。PPTX 导出时如果页数多，可以分批渲染，避免内存峰值过高。FontTools 的字体加载已经用了 @lru_cache，但如果部署多 Worker 实例，每个实例都要加载一次，可以考虑把度量结果缓存到 Redis。

CI/CD 方面，推荐用 GitHub Actions 跑 make test + make lint + make regression，Docker 镜像构建后推送到 registry，再部署到云主机或 K8s。

安全加固

面向真实用户的⁢⁢⁢产品，安全性是不能忽视؜؜؜的。当前项目在安全方面做了 J⁢⁢⁢WT 鉴权、项目归属校验、‎‎‎路径穿越防护等基础设计，但​​​还有几个方向值得加强。

第一是内容审核⁢⁢⁢。用户输入的主题和长文本是开放式的，可؜؜؜能包含不当内容。可以在输入解析阶段⁢⁢⁢增加一层内容安全检查，接入阿里云内‎‎‎容安全或腾讯云天御 API，拦截涉​​​及暴力、色情等敏感内容的请求。

第二是接口限流。每次生成都会消耗 LLM 调用额度，如果有人恶意刷接口，API 费用会暴涨。可以用 FastAPI 的限流中间件（如 slowapi），基于用户 ID 做请求频率限制，比如每个用户每小时最多创建 10 个项目、每天最多生成 50 页。gFVrYVzxL8tKUz/34qdnmJpTKEG8xBm2b32DT6NwTSc=

第三是导出水印。企业场⁢⁢⁢景下，导出的 PPTX 可能需要带上版权水؜؜؜印或用户标识。python-pptx 支持⁢⁢⁢在母版页上添加文本框或图片作为水印，对所有页‎‎‎面生效。可以做成可配置的：开发环境关闭，​​​生产环境根据用户等级决定是否添加。

第四是操作审计⁢⁢⁢。记录关键操作的日志（创建项؜؜؜目、生成、导出、删除），包含⁢⁢⁢用户 ID、操作时间、请求‎‎‎参数等。审计日志不仅用于安全追​​​查，也是分析用户行为的数据基础。

国际化和多语言

项目当前的⁢⁢⁢提示词、UI 文案؜؜؜和默认主题都是中⁢⁢⁢文的。如果要面向海外‎‎‎用户或双语团队，国​​​际化是必须做的事情。

前端国际化可以用 react-i18next，把所有 UI 文案抽取到 JSON 语言包中，根据用户的浏览器语言或手动选择切换。工作量集中在文案抽取上，组件逻辑不需要改。

后端的国际化更复杂一些。提示词需要按语言准备不同版本，在项目配置中增加 language 字段，生成时从对应语言的提示词模板目录加载。O1q1VE7JQeemqtaCFcT9RnaLwcK7gIoDaahA4dzK8kQ=

主题也需要适配。中文字体和英文字体的排版特征差异很大，CJK 字符等宽但拉丁字符变宽，同样的文字量在不同语言下的占用空间不同。主题 JSON 的 font 字段已经分开声明了 web 和 pptx_latin / pptx_east_asian，但度量和溢出检测也需要按语言做适配。
